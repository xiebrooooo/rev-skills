# bench — does the skill actually work?

`verify.sh` answers "is this skill wired up correctly". It cannot answer "is an agent
following this skill any good", because that depends on the model, the harness, and the
fixture.

This directory answers the second question, and it is the reason the README can make a
claim about accuracy instead of just about existence.

**Status: not implemented yet.** The layout and the intended method are recorded here so the
shape is fixed before anyone writes it.

---

## The claim this produces

A single number per skill, with the fixture set behind it:

```
binary-triage    9/12 gradient    accuracy 75%   (25 runs, 3 fixtures, 5 repeats)
```

That number, published in the README and regenerated by CI, is the difference between
"I wrote some prompts" and "I measured this". Very few skills repositories publish one.

---

## Method

For each skill, for each fixture, for each repeat:

1. Fresh agent context. No memory of the previous run.
2. Give the agent the skill body and the fixture path. Nothing else.
3. Capture the agent's output verbatim.
4. Grade against `expected.md` using the **required recoveries** table.

### Grading is per-claim, not per-file

Each row of the `required recoveries` table is one graded claim. A run scores
`claims_passed / claims_total`, so a partially correct run is visible rather than rounded to
zero.

This matters for `triage_packed` in particular, where the whole point is that two of four
plausible answers are wrong in a specific way. Binary pass/fail would hide the distinction
between "localised the entropy correctly but chose the wrong NEXT" and "never localised it
at all".

### Fixtures need a gradient, not just three binaries

A useful bench needs samples that separate competence levels:

| Level | Fixture kind | Should be answered by |
|---|---|---|
| easy | normal, unstripped, known compiler | any working agent |
| medium | stripped, or packed with a known packer | an agent actually following the steps |
| hard | high-entropy data section that is **not** packing | an agent that reads evidence instead of applying a threshold |
| adversarial | a fixture whose naive heuristic gives the wrong answer | nobody reliably; that is the point |

`skills/binary-triage/fixtures/triage_packed` is already a hard fixture — it is the control
that catches threshold-following.

### What is recorded per run

```json
{
  "skill": "binary-triage",
  "fixture": "triage_packed",
  "repeat": 1,
  "model": "<provider>/<model>",
  "claims": [
    {"claim": "blob named as the dense region", "status": "passed"},
    {"claim": "kind=data", "status": "passed"},
    {"claim": ".text not reported as high entropy", "status": "failed",
     "evidence": "output listed .text at 6.25 under PACKING, contradicting step 5"}
  ]
}
```

Raw outputs are kept for inspection. A bench whose failing cases cannot be read is not a
bench, it is a scoreboard.

---

## Rules

- **Deterministic grading only.** No model grades another model's output. Every claim is
  checked by string or structural assertion.
- **Published in full.** `results.md` is generated, committed, and lists every failing case.
  Publishing only the pass rate is how benchmarks become marketing.
- **Reproducible.** Model, harness version and date are recorded per run. A number without
  its provenance is not evidence.
- **No tuning against the bench.** Fixtures added to raise a score are removed. The bench
  measures the skill; the skill does not get rewritten to fit the bench.

## Layout

```
bench/
├── run_bench.mjs      driver — not yet implemented
├── graders/           per-skill claim checkers
│   └── binary-triage.mjs
├── runs/              raw outputs, gitignored
├── results.md         generated summary, committed
└── results.json       generated detail, committed
```

`results.md` is regenerated by `.github/workflows/bench.yml`, not hand-edited.
